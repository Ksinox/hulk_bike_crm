# Процесс работы по карте действий (внутренний документ)

Служебный документ разработки. Заказчику не отдаём — он видит [`ROADMAP.md`](../ROADMAP.md) и страницу «Развитие» в CRM.

---

## Правило работы по каждому пункту

1. Выбираем пункт (чиним баг / добавляем модуль).
2. **Снимаем «было»** — скриншот текущего состояния (для отчёта заказчику).
3. Делаем правку. **UX/UI — часть задачи:** компактно, без нагромождения, вписывать в существующие блоки, удобно ЧЕЛОВЕКУ.
4. Деплой на **preview**.
5. Разработка **сама заходит на preview через MCP-браузер**, кликает, проходит сценарий, снимает скриншоты «стало», проверяет что работает и что вёрстка не поехала.
6. Ставим галочку **«Сделано»** → заказчик проверяет → он ставит **«Принято»**.
7. Скриншоты «было/стало» + описание идут в данные страницы «Развитие».

## 🔒 Главное правило мержа в прод

**В `main` уходит ТОЛЬКО то, что заказчик лично принял** (обе галочки).

Одновременно в работе может быть несколько пунктов. Принял два из пяти — в прод едут только эти два, остальные живут на preview до приёмки. Принял всё — мержим всё.

## Ветки

| Ветка | Назначение |
|---|---|
| `main` | прод. Только принятые пункты |
| `task/<N>-<slug>` | один пункт = одна ветка, от `main` |
| `preview` | сборная: `main` + все ветки в работе. К ней привязан Dokploy preview |

**Цикл:**
1. `git checkout main && git checkout -b task/9-overdue-fine`
2. Работаем, коммитим в ветку пункта.
3. Вливаем ветку в `preview` → `python scripts/redeploy_preview.py` → тестируем.
4. Заказчик принял → вливаем ветку пункта в `main` → релиз в прод.
5. Пересобираем `preview` от свежего `main` + оставшиеся ветки.

⚠️ Preview-апки Dokploy (`8kPYu5M59D2_TP9h4hoxx` api, `nOTMp8wvR-co0HGXA5gkZ` web) переведены на ветку **`preview`** (2026-08-24). Ветка `feature/redesign-application-dossier` — архив прошлых релизов, больше не используется.

## Скриншоты «было / стало»

- **«Было» снимать ДО правки.** Пока релиз не смержен, прод = «было», preview = «стало» — удобный источник парных скриншотов.
- Новые функции (напр. Z-отчёт) снимаем как мини-туториал: где кнопка → что открывается → как пользоваться.
- Файлы кладём в `apps/web/public/progress/` (попадают в бандл, доступны странице «Развитие»).

## Уточнения заказчика (получены 2026-08-24)

### Пункт 1 — Ключ директора

- **Отдельный пароль**, который знает только настоящий директор. Вводится **при каждом** защищённом действии.
- Роли пока НЕ разделяем: менеджеры работают под директорской сессией. Пароль — единственный барьер.
- **Главный сценарий — удалённое подтверждение:** менеджер запускает защищённую операцию → появляется стилизованное окно «введите пароль» → менеджер пароля не знает → звонит директору → **директор заходит с телефона**, видит «висящее подтверждение», знакомится с операцией и подтверждает паролем.
- В окне подтверждения — **краткий отчёт об операции**: что именно произойдёт и на что это повлияет. Компактно и понятно.
- Нужен удобный мобильный экран очереди висящих подтверждений.

### Пункт 11 — Партнёрская техника

- Процент инвестора задаётся **на единицу техники**.
- Нужен **отдельный раздел**, где техника помечается как партнёрская и задаётся её процент.
- Текущая договорённость — **50 / 50** (50 % компании, 50 % партнёру), но процент может меняться → хранить на технике, не хардкодить.
- В расчётах чётко разделять **нашу выручку и выручку партнёра**. Критично для общей выручки и будущего раздела «Аналитика» — перепутать нельзя.

### Пункт 15 — Нумерация скутеров

- **Общее количество мест = число скутеров, доступных к аренде** (это и есть максимум).
- Существующей технике номера **раздать автоматически по текущему порядку**, с возможностью поменять вручную. Менять можно **только на свободные** номера.
- **Дублей быть не должно.**
- Порядковый номер — **новая отдельная сущность**. То, что раньше служило номером, становится настоящим **ID (по 4 последним цифрам рамы)**.

### Пункт 4 — причины возврата

- Список причин **растёт**: «свой вариант с сохранением» добавляет причину в общий список для будущих закрытий.
- **Сохранить** — без подтверждения; **удалить** причину из списка — с подтверждением.

### Пункт 5 — «Новая сделка»

- В «Клиентах» уже есть кнопка **«Создать сделку»** с выпадающим списком — **переиспользовать её механику** на дашборде.
- Пункты списка открываются **по мере готовности** модулей (неготовые — недоступны/«скоро»).
- Все такие окна — современный удобный дизайн в наших цветах: крупные кнопки, пошаговые действия, ничего мелкого.

### Пункт 13 — «своё пространство» аренды

- Смысл: аренда — «отдельное государство». Рядом появятся такие же самодостаточные ветки: **Продажа**, **Выкуп** и т.д. (отдельные вкладки).
- Полное разделение — при создании модулей продаж/выкупа; в рамках пункта 13 — блок показателей аренды (в аренде / готов к аренде / активная / ДТП).

### Пункт 7 — Z-отчёт

- **Это НЕ кассовый Z-отчёт** с закрытием смены.
- Это **сводка за текущие сутки** (с 00:00 до 00:00 следующего дня), доступная **в любой момент дня**.
- Открыл в середине дня — видишь показатели на текущий момент. Удобная оперативная сводка.

## Страница «Развитие» (отчёт заказчику внутри CRM)

Цель: заказчик (Данил) заходит в CRM и **видит прогресс по своим пунктам** — что сделано, что в работе, что принято, со скриншотами «было/стало».

**Где:** отдельный раздел в меню рядом с «Что нового».
**Данные:** `apps/web/src/data/progress.ts` — статус каждого пункта + скриншоты + описание.
**Содержимое:** общий прогресс-бар и разбивка по группам · список пунктов с текстом заказчика и статусом · по принятым — «было/стало» и туториал для новых функций.
**Паритет:** десктоп + мобила обязательно.

Мержится в прод отдельно от пунктов (это витрина работы, а не пункт ТЗ).
